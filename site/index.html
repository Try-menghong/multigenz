Your coding agents, run as a team that can't merge broken work.

MultiGenz splits a goal into tasks, hands each one to Claude Code, opencode, Cline or Codex in its own sandbox and Git worktree, runs your tests on the result, and commits only what passes to a branch it owns. It never pushes.

curl -fsSL https://try-menghong.github.io/multigenz/install | bash

Linux only. Installs into ~/.multigenz and links ~/.local/bin/multigenz. No sudo.

~/demo

How a run works

Every task moves through the same states. The model never decides that a task succeeded; MultiGenz does, from evidence it gathered itself.

  1. planning

    Plan

    A planner agent proposes a task graph. Cycles, unknown dependencies and overlapping file ownership are rejected before anything runs.

  2. running

    Isolate

    Each task gets its own Git worktree and a user-namespace sandbox: read-only system, one writable workspace, no host secrets.

  3. validating

    Verify

    Changed paths, file modes, sizes and credential patterns are checked, then your own test profile runs on an exported copy.

  4. ready

    Repair

    A failed attempt goes back to the agent with the exact failures, within the attempt limit you set.

  5. succeeded

    Integrate

    Validated work lands as one commit on multigenz/run-<id>/integration, tested again after the merge.

Agents

MultiGenz drives the coding-agent CLIs you already use, with their own logins. An agent is enabled only after its flags are found in that binary's own --help. The status column says how far each one has actually been tested.

“Local test model” means the real CLI ran inside the MultiGenz sandbox against a scripted model server, through planning, coding, validation and integration. Codex's own sandbox cannot start inside MultiGenz's, so Codex only runs if you accept relying on the MultiGenz sandbox alone.

Guarantees

These hold no matter what an agent writes in its output.

  • Your checkout is never touched.Work happens in separate worktrees on multigenz/run-<id>/… branches. Your branch and uncommitted files stay as they were.
  • Nothing is pushed or deployed.There is no push command in MultiGenz. You merge the integration branch yourself when you are satisfied.
  • No sandbox, no run.If isolation is unavailable, the run refuses to start. It never falls back to running agents unsandboxed.
  • Only your test commands run.Planner-suggested commands are ignored; fixed test profiles from your policy decide success.
  • Logins stay scoped.Each agent sees only the credentials you name for it, mounted read-only. Logs and reports are redacted.

Get started

Install, let MultiGenz find your agent CLIs, then point it at a repository with tests.

# 1. install
curl -fsSL https://try-menghong.github.io/multigenz/install | bash

# 2. write a policy with the CLIs found on PATH
multigenz init
multigenz doctor

# 3. run a goal against a repo
multigenz run "Add input validation with tests" --repo ./app

# 4. review, then merge yourself
git -C ./app log multigenz/run-<id>/integration
  • Linux with unprivileged user namespaces (unshare)
  • git 2.38 or newer
  • Python 3.12 or newer, or uv to provide it
  • At least one agent CLI, logged in
MultiGenz is local-first: it runs on your machine with your agents' own logins. Agent usage counts against those plans. Source · Security model
